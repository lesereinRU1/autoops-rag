# 应用层整改说明

> **Historical / stale / 历史版本材料。** 本文保留整改过程，当前实现边界以 `docs/current-status.md` 和代码为准。

## 这次处理的范围

本轮没有接入外部大语言模型，先完成评测、失败分析、拒答门控和工程可靠性。模型接口已经封装，但只有在 `.env` 中配置兼容接口后才会调用；当前调用次数和token均为0。

## 应用层评测

新增 `data/eval/application_questions.jsonl`、JSON Schema和锁文件。现有20题由项目内自查，包含15道可回答题和5道不可回答或危险请求题；5道可回答题来自官方手册，尚未达到独立评测要求。

评测脚本分别记录检索命中、正确证据排名、事实字符串覆盖、引用存在、工具选择、拒答、耗时和每题失败类型。数据集不满足60题、70%官方资料、10道不可回答题和30道独立审核题的门槛，因此报告中的 `ready_for_resume_accuracy_claim` 为false。

同一锁定数据集的结果：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| Retrieval Recall@5 | 1.0000 | 1.0000 |
| Retrieval MRR@5 | 0.7778 | 0.7778 |
| 事实字符串覆盖 | 0.3667 | 0.9667 |
| 引用存在率 | 1.0000 | 1.0000 |
| 不可回答题拒答率 | 0.0000 | 1.0000 |

事实字符串覆盖只检查已列出的必要字符串，不等同于语义层Answer Correctness；引用存在率也不等同于每句话都被证据支持。

## 失败驱动修改

- 对未知故障码、未入库版本、其他厂商设备和危险强制操作增加确定性拒答。
- 表格行作为完整证据参与抽取，避免只取表头而漏掉数值。
- 流程类问题从最高相关切片保留多条连续步骤。
- 中英文Query扩展和二次排序曾进行候选实验，但使Recall@5下降，因此默认关闭，没有用局部排名提升换取总体召回下降。
- 最终bad case剩余1道事实字符串不完整、6道正确证据未排第一；后续优先处理排序和独立标注，不再盲目改参数。

## 工程可靠性

- 查询使用并发读锁，索引重建和关闭使用独占写锁。
- 搜索和问答接口最多同时处理8个请求，超时30秒，单客户端每分钟上限300次。
- 每个响应返回请求编号和服务端耗时响应头。
- 本地Qdrant仍只允许单进程；已增加Qdrant Server URL配置入口，多worker部署前必须迁移。
- 外部模型客户端支持一次重试、token统计和本地抽取式降级；当前未配置模型。
- 修复后台启动脚本记录父进程而不是实际监听进程的问题。

12请求小样本并发结果：单并发P50为249.88毫秒；8并发吞吐4.668请求/秒、P95为2406.08毫秒。并发读提高了吞吐，但本机CPU向量计算和SQLite写入仍会增加尾延迟。

## 后续顺序

1. 将评测集扩充到60题以上，并由独立人员复核官方手册证据和必要事实。
2. 针对6道排序靠后的题做可回退对照，不降低Recall后再启用。
3. 最后接入Qwen等兼容接口，增加语义事实正确率、引用支持率和人工可用率评测。
