## 2. 逐项用途和处理建议

### 2.1 Application eval 文件

| 路径 | 可能用途 | 当前判断 | 建议处理 |
|---|---|---|---|
| `data/eval/application_eval.lock.json` | 保存 application eval 数据集路径、SHA-256、冻结时间和范围，用于防止运行过程中数据集变化 | `benchmark_application.py` 和 `llm_smoke_test.py` 直接读取 | **暂时保留但不提交**；v32 与 schema、questions 一起审核并提交，不建议永久忽略 |
| `data/eval/application_eval.schema.json` | 约束应用层评测题字段结构 | 当前脚本未直接引用，但应作为 application dataset 的格式说明 | **暂时保留但不提交**；v32 确认 schema 与脚本一致后提交 |
| `data/eval/application_questions.jsonl` | 20 题应用层评测/LLM smoke 数据，覆盖可回答、不可回答、安全、引用和工具选择 | `benchmark_application.py`、`llm_smoke_test.py` 直接读取，已有报告也引用 | **暂时保留但不提交**；作为 v32 的核心输入，人工复核后与脚本、schema、lock 成组提交 |

这三个文件不应拆开处理。只提交 questions 而不提交 lock/schema，会降低复现性；只提交脚本而不提交 questions，新克隆的项目无法运行对应评测。

### 2.2 Formal eval 旧草稿

| 路径 | 可能用途 | 当前判断 | 建议处理 |
|---|---|---|---|
| `data/eval/formal_questions_draft_011_030.jsonl` | 早期 formal_011～030 候选题草稿 | 20 题均为 `needs_review`，gold 为空；其中 formal_011～013、024～030 已与正式集 ID 重叠，formal_014～023 未进入当前正式集 | v27 可先对该**精确文件名加入 `.gitignore`**，保留本地内容但停止污染 status；后续人工确认未使用的 014～023 是否还有价值，再删除或归档，不能合并进正式集 |

风险：该草稿存在重复 ID，误传给正式校验或误合并会破坏 formal eval 的全局唯一性。不要使用通配规则忽略所有 `*_draft_*.jsonl`，否则未来人工草稿也可能被无意隐藏。

### 2.3 旧检索和多轮回归集

| 路径 | 数据规模和字段 | 当前用途 | 建议处理 |
|---|---|---|---|
| `data/eval/gold_questions.jsonl` | 15 题，包含 `expected_tool` 与 `gold_chunk_ids` | `benchmark_gold.py`、`benchmark_runtime.py` 直接读取；旧评测说明和操作手册引用 | 若保留这些脚本，数据也应在人工检查后作为 **legacy regression fixture 提交**；若决定废弃旧口径，应在后续版本中连同脚本和旧文档一起删除，不要只忽略数据 |
| `data/eval/memory_questions.jsonl` | 3 组首问/追问，含 expected tool/contains | `benchmark_memory.py` 直接读取 | 数据量小且是多轮回归必需，确认无敏感问题后建议 **提交** |
| `data/eval/questions.jsonl` | 24 题关键词/预期词验收集 | `benchmark.py` 直接读取，操作手册引用 | 若继续保留最小检索验收脚本，建议标记为 legacy smoke dataset 后 **提交**；不要与 60 题 formal eval 混称 |

这三份数据都可能包含旧评测口径。提交时必须在文件说明或评测文档中注明它们是 legacy/smoke/regression 数据，不是当前 formal test。

### 2.4 `data/raw/`

该目录不能使用同一种处理方式，应拆成 PDF、下载清单和项目补充资料。

| 文件类型 | 用途 | 风险 | 建议处理 |
|---|---|---|---|
| 3 个 Siemens PDF | 原始官方手册，供入库使用 | 约 53.9 MB；存在版权、版本和仓库体积风险 | **加入/保留 `.gitignore`，本地保留但不提交**。当前 `data/raw/*.pdf` 已覆盖根目录 PDF；建议补充递归规则 `data/raw/**/*.pdf` 防止未来子目录 PDF 被误提交 |
| `data/raw/sources.json` | 资料下载清单，包含 filename、title、model、version、URL、license note、bytes、sha256 等 | 不含 PDF 正文，但 URL、许可说明和哈希需人工核对 | `download_data.py`、ingestion 和 status 直接使用，建议审核后 **提交**，否则首次初始化无法下载资料 |
| 3 个 `autoops_*.md` | 项目自建的地址检查、安全边界和故障排查补充资料，会被 ingestion 直接入库 | 可能包含自编规则；如果来源不明，容易与官方手册混淆 | 确认是可公开的项目自建/合成资料并加来源说明后 **提交**；若含企业经验或私有信息，则暂时保留不提交并制作脱敏公开版 |

不建议把整个 `data/raw/` 加入 `.gitignore`。这样会同时隐藏 `sources.json` 和三个小型补充文档，公开仓库的初始化脚本将缺少下载入口或关键示例资料。

### 2.5 `data/seed/`

| 路径 | 用途 | 当前判断 | 建议处理 |
|---|---|---|---|
| `data/seed/alarms.json` | 9 条结构化故障码种子数据 | `MemoryStore` 启动时读取并写入 `alarm_codes` | 核对来源和许可后 **提交** |

## 3. 风险说明

### 3.1 原始资料和版权风险

- `data/raw/*.pdf` 是原始官方手册，体积大且可能受版权限制，不应直接提交 GitHub。
- `sources.json` 的 `license_note`、下载 URL 和版本信息需人工核对，README 应说明原始资料版权归原权利方。
- `autoops_*.md` 虽然体积小，但需要确认是否完全为项目自建内容，不能把企业内部经验误当公开资料。

### 3.2 敏感数据风险

- 本次只做了凭据形文本的静态扫描：未在上述 JSON/JSONL/Markdown 中发现 Authorization、Bearer、`sk-`、`API_KEY=`、常见私网 IP 或 `C:\Users\...` 路径。
- 该扫描不能证明数据一定可公开。问题文本、设备参数、故障案例和补充资料仍需人工阅读确认是否含企业、人员或现场信息。
- 原始 PDF 和 Trace 即使不含密钥，也可能包含版权或业务敏感内容。

### 3.3 旧评测数据风险

- `questions.jsonl`、`gold_questions.jsonl`、`memory_questions.jsonl`、`application_questions.jsonl` 分别属于不同历史阶段。
- 如果 README 或简历把这些数据与当前 60 题 formal eval 混在一起，会造成题数和准确率口径混乱。
- 旧 gold 依赖当前 chunk ID；重新入库或切分算法变化后可能失效。
- `formal_questions_draft_011_030.jsonl` 与正式集存在 ID 重叠，风险最高，不应参与任何正式评测。

### 3.4 运行完整性风险

- 直接忽略 `data/seed/` 会让结构化工具数据缺失。
- 保留 benchmark 脚本但不提交它所需的小型评测数据，会导致公开仓库中的命令无法复现。
- 不提交 `sources.json` 会使 `download_data.py` 无法读取资料清单。

## 5. 推荐的 v27 最小清理方案

本轮要求不删除、不移动文件，因此推荐下一步 v27 只做以下最小改动：

### 5.1 `.gitignore` 只增加两条有明确理由的规则

```gitignore
# Superseded formal-eval draft with duplicate IDs; keep local until manual review.
data/eval/formal_questions_draft_011_030.jsonl

# Raw manuals may be placed in nested folders; never commit PDF binaries.
data/raw/**/*.pdf
```

说明：当前 `data/raw/*.pdf` 已忽略根目录 PDF，第二条用于覆盖未来子目录。不要添加以下宽泛规则：

```gitignore
data/raw/
data/seed/
data/eval/*.jsonl
reports/*.md
```

这些宽泛规则会隐藏运行必需数据、评测集或项目文档。

### 5.2 其他文件保持现状

- 不删除真实数据。
- 不改业务代码。
- 不改 `data/eval/formal_questions.jsonl`。
- 不修改旧评测内容。
- 不在 v27 顺手提交未经审核的 seed/raw/eval 文件。
- v27 只提交 `.gitignore` 修改和本报告。

这个方案不会立即让 `git status` 完全为空，但能先隔离确定过时且有重复 ID 的草稿，同时避免为“看起来干净”而误删运行数据。剩余文件应按主题分批审核和提交。

## 6. v32 Application Eval 单独处理范围

v32 建议集中处理以下文件：

### 核心数据文件

```text
data/eval/application_questions.jsonl
data/eval/application_eval.schema.json
data/eval/application_eval.lock.json
```

### 相关脚本

```text
scripts/benchmark_application.py
scripts/llm_smoke_test.py
```

### 相关文档与报告

```text
reports/应用层整改说明.md
reports/llm_smoke_test_report.md
reports/评测方法说明.md
```

### v32 应完成的检查

1. 明确 application eval 与 60 题 formal eval 的用途差异。
2. 确认 20 题是 smoke/regression 还是独立 application eval，不重复宣传准确率。
3. 校验 schema 与 questions 实际字段一致。
4. 人工复核 question、gold、required fact groups、source scope 和 review status。
5. 重新生成并验证 lock 文件的 SHA-256，不手工伪造。
6. 检查问题和 gold 是否仍对应当前 chunks。
7. 把旧的整改说明整理成当前口径，过时数字移入历史记录。
8. 决定 `gold_questions.jsonl`、`memory_questions.jsonl`、`questions.jsonl` 是否继续作为独立 legacy regression fixtures；不要自动合并进 application eval。
9. 提交时将 questions、schema、lock、脚本和说明放在同一个可审计变更中。

## 7. 提交前检查建议

后续真正清理或提交前，至少执行：

```powershell
git status --short
git check-ignore -v data\raw\siemens_s7_1200_system_manual_v4_6.pdf
git grep -n -I -E "Authorization|Bearer|sk-|API[_-]?KEY"
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe scripts\validate_formal_eval.py
```

不要把真实 API Key 直接写入搜索命令。对将要提交的 JSONL 和 Markdown 仍需人工阅读，自动扫描只用于辅助。

## 8. 结论

当前 untracked 文件不是同一种“垃圾文件”：

- 原始 PDF 应忽略。
- Formal 011～030 旧草稿存在重复 ID，适合精确忽略并待确认删除。
- Application eval 三件套应留给 v32 成组处理。
- Legacy benchmark 数据决定了旧脚本能否复现，不能只删数据不处理脚本。
- `sources.json`、项目补充 Markdown 和 `data/seed/` 可能是公开仓库正常运行所必需，审核后更适合提交，而不是加入 `.gitignore`。
- 两份旧 Markdown 报告应按历史文档或 v32 application eval 文档处理，不宜全局忽略。

v27 最稳妥的做法是只增加精确 `.gitignore` 规则和本报告，不删除真实数据、不改业务代码、不碰 formal eval 正式集。
